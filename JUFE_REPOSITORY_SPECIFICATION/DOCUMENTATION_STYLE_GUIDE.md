# JUFE Documentation Style Guide

## Purpose

This document defines the editorial and formatting standards used throughout the JUFE repository.

Its purpose is to ensure that every document presents information in a consistent, readable, and maintainable manner, regardless of when it was written or who contributed to it.

Consistency reduces cognitive load and allows readers to focus on understanding the content rather than adapting to different writing styles.

## Writing Philosophy

Documentation within JUFE exists to communicate understanding.

Every document should strive to:

- explain before instructing
- clarify before expanding
- preserve reasoning rather than merely recording conclusions
- remain accessible without sacrificing precision
- contribute to the long-term stewardship of the repository
  
The purpose of documentation is not simply to record information.

Its purpose is to make knowledge understandable.

## Document Structure

Documents should generally follow the pattern:

```text
Title

Introduction

Purpose

Body

Summary
```

Each section should answer one clear question before progressing to the next.

Readers should never wonder why a section exists.

## Heading Hierarchy

Use Markdown headings consistently.

```md
# Document Title

## Major Section

### Subsection

#### Supporting Topic
```

Only one # heading should appear within each document.

## Paragraph Structure

Paragraphs should remain concise.

Each paragraph should communicate a single primary idea.

Where appropriate, separate concepts into individual paragraphs rather than creating large blocks of text.

White space improves readability.

## Emphasis

Use emphasis sparingly.

**Bold**

Used for:

- foundational principles;
- important conclusions;
- key repository concepts.
  
Example:

**Understanding comes before implementation.**

*Italics*

Used for:

- questions;
- gentle emphasis;
- document titles where appropriate.
  
Example:

*Why was this decision made?*

Avoid excessive emphasis.

If everything is emphasised, nothing stands out.

## Block Quotes

Use block quotes to highlight foundational principles or reflective questions.

Example:

> **Knowledge before implementation.**

or

> *What evidence supports this idea?*

Block quotes should be used intentionally and sparingly.

## Lists

Use unordered lists for principles and collections.

Example:

- Knowledge before implementation
  
- Clarity before complexity
  
- Traceability before assumption
  
Avoid unnecessary punctuation unless each item forms a complete sentence.

## Horizontal Rules

Use horizontal rules to separate major document sections where appropriate.

---

This creates natural visual separation within longer documents.

## Tone of Voice

Documentation should remain:

- calm;
- precise;
- professional;
- welcoming;
- explanatory;
- technically rigorous.
  
Avoid unnecessary marketing language, exaggeration, or emotionally persuasive writing.

Allow the ideas to speak for themselves.

## Repository Perspective

Documentation should describe the repository rather than the author.

Prefer:

The repository is designed...

rather than

I designed...

This ensures the documentation remains timeless.

## Chapter Summaries

Where appropriate, conclude each chapter with a brief summary.

The summary should:

- reinforce the chapter's purpose;
- prepare the reader for the following chapter;
- avoid introducing new concepts.
  
## Guiding Editorial Principles

Every document should aim to leave the repository clearer than it was before.

Before finalising any document, ask:

*Does this improve understanding?*

If the answer is yes, the document is moving in the right direction.
